# Create Replication Job

---

## Overview

A replication job synchronizes the storage of a VM or container from its current node to another node in the VM2Cloud cluster.

The first synchronization transfers the required guest data to the target node. Subsequent synchronizations transfer only changed data.

Replication is useful when a guest needs a synchronized copy on another cluster node for faster recovery or migration.

---

## When to Use

Create a replication job when:

* A VM or container requires a copy on another cluster node.
* Shared storage is not being used for the guest.
* Faster recovery after a node failure is required.
* You want to reduce the amount of data transferred during a later migration.
* A guest needs replication to another cluster node.

Replication is not a replacement for backup.

---

## Prerequisites

Before creating a replication job:

* VM2Cloud must have a working cluster.
* The source and target nodes must be cluster members.
* The guest must already exist.
* The guest must use storage supported by replication.
* The source node must be online.
* The target node must be online.
* The target storage must have sufficient free space.
* Source and target nodes must have reliable network connectivity.
* The cluster must have quorum.
* You must have sufficient permissions to manage the guest and replication configuration.

The documented storage-replication implementation supports local ZFS storage. Verify the storage type used by the VM2Cloud installation before creating the job.

> **Warning:** Replication is not a backup. Maintain a separate backup strategy for production workloads.

# Configuration / Options

## Guest

The guest identifies the VM or container whose storage will be replicated.

The guest must use storage supported by the replication mechanism.

---

## Target Node

The target node is the cluster node that receives the replicated guest data.

Select a target node that:

* Is online.
* Is part of the same cluster.
* Has supported storage.
* Has sufficient capacity.
* Has reliable connectivity with the source node.

---

## Schedule

The schedule determines how frequently the replication job runs.

The underlying replication mechanism supports intervals from:

* Minimum: **1 minute**
* Maximum: **1 week**

The schedule uses a subset of systemd calendar-event syntax.

Choose a shorter interval when:

* The guest changes frequently.
* A smaller recovery-point gap is required.
* Network and storage resources can support the additional synchronization activity.

Choose a longer interval when:

* The guest changes infrequently.
* Network bandwidth is limited.
* Storage performance is constrained.

---

## Bandwidth Limit

The bandwidth limit controls the maximum replication traffic generated by the job.

Use a limit when:

* Replication shares a network with production traffic.
* Multiple replication jobs run simultaneously.
* Storage performance must be protected.
* Cluster network traffic must remain available.

---

# Replication Behavior

## Initial Synchronization

After the job is created, the initial synchronization transfers the required guest data to the target node.

For a large guest, the first synchronization can take significant time.

The duration depends on:

* Guest disk size.
* Amount of data.
* Storage performance.
* Network bandwidth.
* Network latency.
* Target storage performance.

---

## Subsequent Synchronizations

After the initial synchronization completes, later replication runs transfer only changed data.

This is possible because VM2Cloud uses snapshots to identify changes.

Therefore:

```text
Initial synchronization
        ↓
Full initial data transfer
        ↓
Snapshot/change tracking
        ↓
Incremental synchronization
        ↓
Only changed data transferred
```

This reduces network traffic compared with repeatedly transferring the entire guest disk.

---

# Multiple Replication Targets

A single guest can be replicated to multiple target nodes.

Example:

```text
             ┌──────────> Node B
             │
Node A ──────┤
             │
             └──────────> Node C
```

Each target requires its own replication job.

Do not create two jobs for the same guest with the same target node.

---

# Replication and Migration

Replication can reduce the amount of data transferred when a guest is migrated to a node that already contains its replica.

For example:

```text
Before migration:

Node A
   |
   | Replication
   v
Node B
```

If the guest is migrated to Node B, only changes since the last replication may need to be transferred.

If the guest is migrated to a node without an existing replica, the complete disk data may need to be transferred.

---

# Replication Direction After Migration

When a guest is migrated to its replication target, the replication direction automatically changes.

Example:

```text
Before:

Node A
   |
   v
Node B
```

After the guest moves to Node B:

```text
Node B
   |
   v
Node A
```

This allows the replication relationship to continue after the guest changes its current node.

# Common Issues

## Target Node Is Not Available

### Possible Causes

* Target node is offline.
* Network connectivity is unavailable.
* Cluster communication is failing.
* Node is not a cluster member.

### Resolution

1. Check the target node status.
2. Check cluster status.
3. Check node network connectivity.
4. Check Corosync if cluster communication is affected.
5. Restore node availability.
6. Run the replication again.

---

## Replication Job Does Not Appear

### Possible Causes

* Job creation did not complete.
* Incorrect guest selected.
* Permissions are insufficient.
* UI configuration was not saved.

### Resolution

1. Return to the guest.
2. Open **Replication**.
3. Check the replication-job list.
4. Check Task History.
5. Confirm that the job was created successfully.
6. Verify administrator permissions.

---

## Replication Fails During Initial Synchronization

### Possible Causes

* Target storage is full.
* Network connection failed.
* Source storage problem.
* Target storage problem.
* Unsupported storage.
* Target node unavailable.

### Resolution

1. Check Task History.
2. Read the replication error.
3. Check source storage.
4. Check target storage.
5. Check free capacity.
6. Check node connectivity.
7. Verify storage compatibility.
8. Correct the underlying problem.
9. Retry synchronization.

---

## Replication Is Too Slow

### Possible Causes

* Large guest disk.
* Slow storage.
* Limited network bandwidth.
* Bandwidth limit configured too low.
* High storage activity.
* Network congestion.

### Resolution

1. Check source storage performance.
2. Check target storage performance.
3. Check network utilization.
4. Check the configured bandwidth limit.
5. Check for other concurrent replication jobs.
6. Correct the bottleneck.
7. Monitor the next synchronization.

---

## Target Storage Is Full

### Resolution

1. Select the target node.
2. Open the affected storage.
3. Check storage usage.
4. Identify what is consuming the available space.
5. Free space or expand the storage.
6. Confirm that sufficient space is available.
7. Retry the replication.

> **Warning:** Do not manually delete replication data unless you understand the effect on the replication job.

---

## Quorum Is Lost

A replication job may not operate correctly when the cluster has lost quorum.

### Resolution

1. Check cluster quorum.
2. Check **Expected Votes**.
3. Check **Total Votes**.
4. Check node availability.
5. Check Corosync.
6. Restore cluster communication.
7. Verify quorum.
8. Check the replication job again.

---

# CLI Verification

CLI is secondary.

Use it only when the UI does not provide sufficient information for troubleshooting or verification.

## Display Replication Status

Run:

```bash
pvesr status
```

Review the configured replication jobs and their current status.

The underlying storage replication framework is managed by the `pvesr` utility.

---

## Check Cluster Status

If replication appears to fail because of a cluster problem:

```bash
pvecm status
```

Verify:

* Cluster membership.
* Expected votes.
* Total votes.
* Quorum state.

---

# Safety Considerations

> **Warning:** Do not manually delete replicated guest data from the target storage to resolve a replication error.

> **Warning:** Do not manually start the replicated guest on the target node while the original guest may still be running on the source node.

Before manually recovering a replicated guest:

1. Confirm the source node state.
2. Confirm whether the original guest is still running.
3. Check HA state if HA is enabled.
4. Verify fencing when applicable.
5. Confirm the target replica is usable.
6. Follow the appropriate recovery procedure.

Running the same guest simultaneously on two nodes can result in data corruption.

---

# Best Practices

* Use supported storage.
* Verify target storage capacity before creating the job.
* Use reliable cluster networking.
* Select a target node appropriate for recovery.
* Configure the replication interval according to the workload.
* Avoid unnecessarily short replication intervals.
* Use bandwidth limits when required.
* Monitor replication tasks.
* Investigate failed synchronization immediately.
* Maintain independent backups.
* Test recovery procedures.
* Document replication targets.
* Avoid placing all replicas on the same physical failure domain.

# Summary

A replication job synchronizes a VM or container from its source node to a target cluster node.

The basic workflow is:

```text
Select Guest
     ↓
Open Replication
     ↓
Click Add
     ↓
Select Target Node
     ↓
Configure Schedule
     ↓
Configure Bandwidth Limit if required
     ↓
Review Configuration
     ↓
Create Job
     ↓
Verify Job
     ↓
Verify Initial Synchronization
     ↓
Monitor Subsequent Synchronizations
```

The first synchronization transfers the initial guest data. Later synchronizations transfer only changed data.

Replication improves recovery and migration capabilities but does not replace independent backups.
